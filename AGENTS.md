# Pro Cards – guide for coding agents

A set of dependency-free Home Assistant custom cards in one HACS bundle, plus a VitePress docs site whose
examples run the real cards against a simulated home. Read this file first; the docs site and the code
explain the rest.

## Rules that are not obvious from the code

1. **Edit `src/`, then `npm run build`.** Never edit `dist/`. A change to a card without a rebuilt `dist/pro-cards.js` fails CI.
2. **Cards stay dependency-free.** No npm runtime deps, no Lit. Every card may import `src/shared/` (including `src/shared/entity/`) and its own folder. A card never imports another card or another card's folder. Colours come from HA theme tokens (`var(--<name>-color)`), never hard-coded hex in CSS (a hex fallback table for blending is fine). Text sizes, weights and fonts come from HA's typography tokens through `src/shared/typography.ts` (`fs`, `type`, `fw`, `font`, `TILE_PRIMARY` / `TILE_SECONDARY`), never a literal px font size in CSS (text inside a drawing that scales with its viewBox is the exception; `600` has no token and stays literal); geometry built around text reads the styled size through the card's `TextCache` (measured once per theme, only once the card is on the page), never a px constant. No fixed pixel widths on cards; grid items need `min-width: 0` and `contain: inline-size`.
3. **Everything under `src/` is a plain TypeScript ES module** (`strict` on, imports carry explicit `.ts` extensions, `npm run typecheck` runs `vue-tsc --noEmit` over the whole repo). Types for the Home Assistant surface live in `src/shared/ha.ts`; `home-assistant-js-websocket` is a type-only devDependency and never reaches the bundle. Pure helpers live in the card's folder (or `src/shared/` when more than one card needs them) and get a unit test that imports them directly; the element files export only their class. The bundle is an iife, so exports cost nothing.
4. **User-facing strings inside the cards go through `t(hass, key)`** (`src/shared/i18n.ts`): English in `src/i18n/en.ts` is the source and the fallback, other languages are one file each in `src/i18n/`, picked by `hass.locale.language`. Never write a rendered word or an editor label as a literal. Defaults must resolve at render time, not in `setConfig` (no `hass` yet). Users' own words (`labels` / `zones` / rule `label`, `title`, `name`) are never translated. Config errors, console messages and the card picker entries stay English.
5. **Docs examples must use entities of the demo world** (`docs/.vitepress/theme/ha-shim/world.ts`). An unknown entity renders as "missing" and looks like a bug.
6. **A docs example is a `::: live` container around a ```yaml fence.** Whole dashboards use `<DashboardGrid b64="…">` followed by the same YAML as a readable fence (both must stay in sync; `.claude/skills/add-example` shows how).
7. **Visual baselines are Linux-only.** Only `npm run test:visual:update` (Docker) may write `tests/visual/__snapshots__/`. Never run Playwright `--update-snapshots` natively.
8. **Template support in the docs shim is `{{ }}` expressions only.** Examples must not rely on `{% %}`.
9. **Keep `hacs.json`, `package.json` version and `CHANGELOG.md` consistent.** Releases are git tags `v*`; the workflow attaches the bundle. Until 1.0.0 ships, the changelog stays "Initial release": nothing before the first release is a change for anyone.
10. **Formatting is Prettier, linting is ESLint, type checking is TypeScript** (`npm run format`, `npm run lint`, `npm run typecheck`; configs in `.prettierrc.json`, `eslint.config.ts` (the JS and typescript-eslint recommended rules) and `tsconfig.json`). A pre-commit hook (husky + lint-staged) formats and lints staged files, and CI fails on unformatted files or lint errors. `dist/` and the visual baselines are ignored; code inside Markdown fences is left untouched so docs YAML keeps its flow style.

## Definition of done

```sh
npm run check          # prettier check + eslint + typecheck + build + schema/unit tests + integration tests + docs build
npm run test:visual    # only when anything rendered changed (needs Docker)
```

Then update `CHANGELOG.md` under the next version and, for behaviour changes, the card's page in `docs/cards/`.

## Conventions

- English for docs, comments and commit messages. Commit messages: imperative subject, body explains why.
- YAML in docs: two-space indent, flow style `{ … }` for short rule entries, block style otherwise.
- Tests: describe behaviour, not implementation; prefer asserting on rendered text, classes and CSS variables (`--fe-color`) over internals.
- Home Assistant specifics worth remembering: sections grid is 12 columns per visible section column; `rows: "auto"` sizes to content; `grid_options` overrides `getGridOptions`.

## Things that look wrong but are intended

- Every card's host takes the height its container gives (`STYLE_HOST`: `height: 100%`), as Home Assistant's own cards do: HA gives the height to the wrapper around an inline `hui-card`, fixed for fixed rows and stretched to the grid row for `rows: auto`, and a horizontal stack makes our host a stretched flex item; where the height follows the content (masonry, a vertical stack) 100% is the content's height. That default needs no script and the cards never read `grid_options`. `fill_height: false` sets a `keep-height` attribute (`syncKeepHeight` in `card.ts`, from the raw config in `setConfig`): the host keeps its content's height (`height: auto`, `align-self: flex-start` for a stack), at most its container's (`max-height: 100%` on a flex column, so ha-card, `overflow: hidden`, shrinks into a smaller cell). Whatever grows into the height keeps an explicit natural height (from the config or the width, never from its own drawing) as its flex basis (`flex: 1 1 auto`, a `min-height` floor) and is drawn at its measured height, never stretched. Never use a flex basis of 0 for it: in a stretched grid row that drops the card's own contribution to the row's height, and the tallest card collapses to the next one. Tiles without a plot centre their content, lists keep their rows at the top unless `vertical_align` (group and sections card) moves them to the centre or the bottom. The test harness and the docs grid (`docs/.vitepress/theme/grid.ts`) lay cards out as HA does: auto row tracks, a definite height on a fixed cell, auto cells stretched to their row.
- `state: "on"` / `"off"` in rules are quoted in YAML on purpose (YAML 1.1 booleans).
- Explicit `color` / `icon` on an entity **override** the rules (fixed look); leave them out to let the value drive the look.
- `tint_card` lives on a rule and does nothing unless that rule matches. Rules match in the order written, first match wins (no sorting).
- The wind card's flow field is a square of at least 480 px (`fieldSize`) inside an `overflow: hidden` band: it is sized from the band's measured box, not the card's layout width, so it covers the band at any rotation. Every particle's base styles carry its animation phase (`--p0`), so a paused frame (`prefers-reduced-motion`, visual tests) still shows a populated field. The band's DOM is rebuilt only when its geometry changes or the waves moved by a real margin (hysteresis in `needsRedraw`, `gustsFor`: streaks come above 16 km/h and go below 8, and `fieldSizeFor`: a field grows a size step at once and shrinks only by two); a speed change scales the playback rate of the running animations (`setRate`), so sensor noise never restarts the flow.
- The rain card's drop count follows the rate, so the field is rebuilt only when rain starts or stops or the count moves by a quarter (at least three drops) (`needsRebuild`); a rate change scales the playback rate. The gauge's wave strip is 110 % wide and loops by 10 % (one period), so no fixed width is needed.
- The power flow card's home `rules` match the home's power in **watts** whatever unit the sensor reports (the tree computes in W). A tree whose first sensor reports no power unit (no energy unit on the energy card) counts in that unit instead (`treeUnit` in `src/shared/flow-tree/model.ts`): values as written, no W/kW switch, `idle_below` 0 unless given, motion by the share of the largest flow. Every column is evenly spaced: one pitch between every two centres, the most any of its labels asks for (`sourceStack`, `columnPlan`; with rooms also what a room's label above it needs from the room before), rooms centred on their devices. The home sits level with the source nearest its height when that one is within two corner radii of it, so its line runs straight; the lanes into the home are mirrored (`laneOffsets`: lane 0 for a level source, else half a lane off the centre with sources on both sides) and turn in one block right before the home (`bendAt`: same radius, a lane apart, the outermost last), and a source label at the home's height keeps the home and that block clear of it. The lines out of the home and out of each room mirror them (`fanOut`): their own lanes centred on the node, turning in one block after it (the outermost first), each lane's turn clear of the label slots beside its leg; the lanes squeeze to `GEOM.lineW + GEOM.minGap` (a 2 px gap between tracks) and where even that does not fit, all of that node's lines share one trunk (`trunkOf`, `forkOf`). The consumer column centres on the home (`acrossOf` gives it as much room after it as before it), and on a narrow card the home moves left for its lanes before they merge (`lanesClear`; only where that makes them fit). The layout reads each label at the widest it has been while the diagram's width, fonts and nodes stay the same (`keepWidest` in `render/tree.ts`), so a value ticking between `990 W` and `1.01 kW` never moves the columns or flips a label's place or shape back and forth. With rooms (direction right) the rooms' labels sit centred above or below them, clear of the home's trunk; a narrow card gives way in this order: the home moves left down to a source label's value (its name cut, `srcCut`), device names are cut where a room's label takes their place (`cutsFor`, never a value), and where the devices' values would not fit beside the rooms' labels the devices take their labels centred below them (`under`; only when the config's device pitch leaves room for that, so the height never depends on the width). The tree's height follows the config (sources, consumers and their label heights) and which of its nodes are shown (`visibility`, `hide_consumers_below`), never the width, so the resize observer cannot loop; only the positions along the flow follow the measured width and the measured label widths (the tree is laid out twice per render: once to know the label texts, once with their sizes). A link keeps its dots through value changes (`setRate`) and through moves (a label that changes its width moves the columns: the link takes its new path in place, `moveLane`); it is rebuilt only when it switches idle ↔ active, changes direction or its dot count moves by two. Tracks and lanes are kept by the link's id, its flow's index, which is the same for one config whatever the values or the hidden nodes. A consumer with a negative value produces (an EV giving back, a plug-in panel): its link runs back to the home in the solar colour and it counts for nothing in the `Other` node.
- A render of an entity card fills only the rows whose inputs changed (`_rowInputs`, `depsChanged` in `src/shared/deps.ts`): a row's model is cached on the states it reads, its templates, the language and Home Assistant's formatting; a row keeps its DOM while its model, pending calls, armed buttons and shown buttons are the same. A row that reads more than its own item (the wind, rain and weather lead) returns null and is filled every time. The end of a gesture (`endDrag`) always fills its row again: a cancelled drag made no call, so no input changed, yet the control shows where the finger was. Anything else a row comes to depend on must go into its inputs, or the row goes stale. Plots, weather sections and the illuminance body are gated the same way; time moves them only by a pixel of their window (or the hour, the day).
- The energy flow card reads its meters from the recorder's long-term statistics (`recorder/statistics_during_period`, in kWh whatever the meter's unit) plus a live tail: the meter's state minus its reading at the end of the last compiled hour, so its numbers move between fetches (every 5 minutes, and at the period's turn, when the new period starts from the meters' readings until its first hour is compiled). The flows split per statistics bucket (hours of a day, days of a month) with Home Assistant's Energy dashboard rule (battery charge from solar before the home), not the power card's order of the moment, and every pair shows both values (`gross`). Its thresholds and rules read kWh, its dots move by a link's share of the home (`shareMotion`), not by an amount. The header's period picker (its calendar is `src/shared/datepicker.ts`, our own: Home Assistant's `ha-date-range-picker` is frontend-internal and lazily loaded; it opens as a `popover` in the top layer, so the card's `overflow` does not cut it; `period_picker`, on by default, the card always has a header – `_buildHeader` / `_headerExtra` in the entity base – titled Energy when the config has no `title`; the picker's button names the period at a fixed width (cut with an ellipsis), so nothing in the header moves when the period changes, and the summary line names the period only without the picker) is the viewer's own and lives in memory only (`_pick`: a day, week, month or year – stepped by its kind – or any range of days, stepped by its length; `kindOfRange` tells them apart): it goes back to `period` after ten minutes untouched, on disconnect and on reload. A closed period never takes the live tail.
- `visibility` on a card is Home Assistant's (it hides the whole card) and the cards never read it, not even on the entity card and the group card, whose top level is otherwise their item / group. On the parts of a card (`src/shared/visibility.ts`, HA's condition semantics: strict `numeric_state`, `not` = not all, a template false until rendered) it decides what is drawn: header items and custom buttons hide in place, the body is rebuilt when the set of shown rows, groups or sections changes (never during a drag or with an open select), the power flow lays its tree out over the shown nodes (`viewConfig`) and hides the rest in place, the multi trend card drops hidden series from the plot. A hidden consumer's watts count in `Other`; a hidden source changes no number. `hide_consumers_below` remembers per consumer whether it was shown, so it comes back only clearly above the threshold.
- The layout card draws no `ha-card` of its own (as Home Assistant's stacks): no border of its own around the cards. Its cards are `hui-card`s, which evaluate the cards' own `visibility`; the layout stops their `card-visibility-changed`, reflows, and hides itself (with `connectedWhileHidden`) when every card is hidden. Its breakpoints are view columns, not pixels: it reads the `--column-span` Home Assistant's sections view sets on each section (already capped by the view's columns) and inherits into the cards; its own body resets it, so a layout inside a layout counts its own width in the sections view's 500 px columns, as one outside a section does. Per-card options live in `view_layout`, the key Home Assistant's card editors keep. A card keeps its `hui-card` through `hass` and `view_layout` changes (`reconcile`), and masonry moves only the cards whose column changes: a moved node reconnects and its card reopens its subscriptions. The schema checks a Pro card inside against its own schema, one `if`/`then` per type: a new card type goes there too.
- The swipe card's strip is the browser's own scroll snapping, no gesture code. Its stops (one dot each) are measured from the cards' offsets (transforms do not count; in RTL from the right, `scrollLeft` running from 0 down) and only again when the width, the cards shown, the config, the theme or the language changed; a measurement at no width (the card hidden) is not kept, and `CardsBase` lays a card out again when it shows after being hidden, at whatever width. The strip has 8 px (`BLEED`) of padding above and below with a negative margin of the same, so the cards' shadows and focus rings are not clipped by its scrolling; only a strip that scrolls takes the focus (`role="region"`).
- A poster (`layout: poster`: the entity card's, or a group's) anchors its content to the bottom of the height it is given, where a tile centres it; its natural height is its content's, so `rows: auto` works too. Its badges are rows of their own (`hval`, `fillBadge`) inside the poster row's `.corner`, built once by `_poster` in the entity base: `fillPoster` fills only the poster's own parts (`.plead`, `.plabel`, `.pbody`) and never clears the corner, so each badge keeps its own row inputs, actions and visibility. The badges are in `group.badgeIdxs`, not `group.idxs`: they hide in place, as header entities do, and never rebuild the body.
- The weather card is a tile without `sections`; with `sections` it renders them in the written order (the hero lead is a section too). Its condition colour ignores HA's state colour (one amber for every condition) and is primary unless a rule or `color` says otherwise.
